# Установка, обновление и удаление

Всё ниже — поведение установщика `legacy/installer/Sora.iss` и поставляемого клиента на текущем HEAD. Готового публичного релиза пока нет: этот документ описывает установщик, собранный по рецепту из [development.md](development.md), а не страницу загрузки.

Главное различие, которое нужно держать в голове: **поставляемый исполняемый файл — клиент на базе v2rayN** (`sora_<цель>.exe`). Новый клиент (`legacy/Client`) в установочный комплект не входит. Где поведение двух клиентов различается, это сказано явно.

## Требования

| Что | Минимум |
| --- | --- |
| Windows | 7 SP1 (по умолчанию; профили установщика для 8.1, 10 и 11 задаются при сборке) |
| Обновления Windows 7 SP1 | KB4490628, KB4474419 и KB3140245: установщик проверяет их на Windows 7 и предупреждает до установки, если не находит; продолжить без них можно вручную — см. шаг 1 ниже |
| Архитектура | x86; на x64 сборка работает через WoW64 (`ArchitecturesAllowed=x86compatible`) |
| .NET Framework | 4.8 |

Права администратора для самой установки не нужны: установка per-user. Повышение прав установщик запросит только для шагов .NET и KB ниже, если они понадобятся.

## Установка

Запустите `Sora-<версия>-<цель>-Setup.exe`. Мастер говорит по-русски и по-английски.

Куда ставится: `%LOCALAPPDATA%\Programs\Sora` (значение по умолчанию). Состав комплекта определяет `legacy/build/Stage-Release.ps1`: исполняемый файл клиента, `xray.exe` и `sing-box.exe` для режима TUN (комплект сверяет их SHA-256 с закреплёнными значениями и прерывает сборку при несовпадении), `tun2proxy` с `wintun.dll`, базы `geoip.dat` и `geosite.dat`, лицензии.

Что установщик делает по шагам (порядок — как в `PrepareToInstall` в `Sora.iss`: сначала проверка обновлений Windows 7, затем KB3033929, затем .NET):

1. **Только на Windows 7 (обе архитектуры) — проверка обновлений, которые установщик поставить не может**: KB4490628 (стек обслуживания, нужен Microsoft для обновлений .NET Framework на Windows 7 SP1), KB4474419 (поддержка подписей SHA-2 для тех же обновлений) и KB3140245 (включает TLS 1.2 в системном SChannel; поставляемый клиент включает TLS 1.2 кодом, и без этого обновления загрузка подписок по HTTPS на чистой Windows 7 SP1 может не работать). Проверка — по установленным пакетам CBS, тем же способом, что и KB3033929 в шаге 2. Если чего-то не нашлось, мастер до установки показывает, чего именно и на что оно влияет, и предлагает выбор: отменить установку и сначала обновить Windows либо продолжить. Честная оговорка проверки: обновление, пришедшее в составе накопительного пакета, записано под номером этого пакета, поэтому «не обнаружено» не всегда значит «не установлено» — для этого случая и нужен ручной выбор, а не жёсткий отказ.
2. **На 32-битной Windows 7** проверяет KB3033929 (поддержка SHA-2 подписей). Если пакета нет — SHA-256 встроенного `.msu` сверяется с закреплённым в скрипте установщика, несовпадение прерывает установку; затем `wusa.exe /quiet /norestart` с повышением прав, при кодах 3010/1641 мастер предложит перезагрузку. На 64-битной Windows 7 этот шаг не выполняется: встроенного 64-битного `.msu` в комплекте нет, а SHA-2-требование там покрывает проверка KB4474419 из шага 1.
3. **Проверяет .NET Framework 4.8**: значение `Release` в `HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full` должно быть не меньше `528040` (проверяются обе ветки реестра на x64). Если 4.8 нет — запускается встроенный установщик .NET: сначала его SHA-256 сверяется с закреплённым в скрипте установщика, несовпадение прерывает установку; запуск — `/q /norestart`, при кодах 3010/1641 мастер предложит перезагрузку.
4. **Копирует файлы** комплекта в каталог установки.
5. **Регистрирует протокол `sora://`** на исполняемый файл комплекта (`HKCU\Software\Classes\sora`, обработчик — `"<exe>" "%1"`). Честная оговорка: поставляемый клиент аргумент `sora://…` сегодня не обрабатывает, переход по ссылке молча игнорируется. Импорт подписки из ссылки реализован в новом клиенте и заработает при смене комплекта; саму регистрацию менять не придётся.
6. **Ярлыки**: в меню «Пуск» — всегда; на рабочем столе и автозапуск — по флажкам мастера, по умолчанию оба выключены. Автозапуск от установщика — ярлык в папке автозагрузки пользователя с параметром `--silent`.

Службу `SoraLegacyCore` этот установщик **не ставит**: поставляемый клиент запускает движки сам. Служба — путь нового клиента и разработки; она регистрируется самой службой (`sora-core --install-service`), см. [development.md](development.md).

## Автозапуск: два механизма

- Ярлык установщика в папке автозагрузки (флажок «Запускать в фоне при входе в Windows»).
- Настройка «запуск при входе» внутри клиента: значение `SoraAutoRun_<MD5 каталога установки>` в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, команда — `"<exe>" --silent`. Имя значения зависит от каталога, поэтому записью в скрипте установщика его не задать; деинсталлятор находит такие значения сканированием (см. «Удаление»).

## Командная строка поставляемого клиента

Контракт, который сегодня работает у пользователя (реализация — `Program.cs` поставляемого клиента). Новый клиент повторяет `--silent`, `--restore-proxy` и `--wait-for` и добавляет импорт по ссылке `sora://`; аргумент `--tun` новый клиент не обрабатывает — известное различие, см. абзац после таблицы:

| Аргумент | Поведение |
| --- | --- |
| `--silent` | запуск без окна, в трей |
| `--restore-proxy` | восстановить системный прокси, записанный до изменений Sora, и выйти. Код 0 — восстановлено или записывать было нечего; 1 — запись повреждена или применить не удалось. Без `--silent` сначала спрашивает подтверждение у пользователя |
| `--wait-for <pid>` | подождать завершения процесса с этим PID, не дольше 15 секунд, затем стартовать |
| `--tun` | стартовать с режимом TUN |

Один экземпляр на путь исполняемого файла: второй запуск не открывает второе окно, а активирует окно работающего экземпляра (адрес окна хранится в `HKCU\Software\Sora`) и завершается.

Различие нового клиента — `--tun`: такого аргумента в нём нет (ни в `ClientContract.cs`, ни в заголовке контракта в его `Program.cs`). Режим TUN новый клиент берёт из сохранённой настройки `ClientSettings.Tun` (по умолчанию включена), а не из аргумента запуска, поэтому после смены комплекта `sora_<цель>.exe --tun` будет молча проигнорирован. Контракты двух клиентов различаются ровно на `--tun` (только у поставляемого) и `sora://` (только у нового).

## Обновление

- **Самообновления у клиента нет.** Пункт проверки обновлений интерфейса просто открывает страницу релизов в браузере. Обновление продукта — ручная установка новой версии поверх старой.
- **Установка поверх**: запустите новый установщик в тот же каталог. Файлы комплекта заменяются. Файл конфигурации клиента `guiNConfig.json` в комплект сознательно не входит, поэтому установщик его не перезаписывает; каталоги данных клиента (`guiConfigs` с подписками и серверами, `guiBackups`) установщик при установке не трогает — настройки и подписки переживают обновление.
- **Движки из интерфейса**: поставляемый клиент умеет обновлять ядра из своего списка (v2fly_v5, SagerNet (v2ray-core), Xray, clash, clash_meta) и геобазы с официальных релизов. Архив ядра до распаковки сверяется по SHA-256 с `.dgst`-манифестом релиза только для ядер v2fly, v2fly_v5 и Xray; несовпадение — отказ, бинарь не заменяется. Для SagerNet (v2ray-core), clash и clash_meta `.dgst`-манифеста у апстрима в предсказуемом виде нет, поэтому проверка хеша для них пропускается (остаётся запись в журнал) и действует только запрет downgrade. Ядро sing_box в список обновляемых из интерфейса не входит — пункта его обновления в меню нет. Движки, которые запускает служба ядра, проверяются строже: служба сверяет каждый бинарь с дайджестом из поставляемого `SHA256SUMS` при каждом обнаружении и не запускает несовпавший.
- **Данные службы ядра** (настройки нового клиента, зашифрованное хранилище подписок и секретов) лежат вне каталога установки, в `%APPDATA%\sora-legacy\core`, и установка поверх их не касается.

## Удаление

Удаление — стандартное, через «Программы и компоненты» или `unins000.exe` в каталоге установки. Деинсталлятор:

1. **Восстанавливает системный прокси**: запускает клиент с `--restore-proxy --silent` и ждёт завершения. Поставляемый клиент переигрывает запись `user-wininet.json`, которую сделал до первого изменения прокси (флаги подключения, сервер, список исключений, PAC-URL), через bundled `sysproxy.exe` и удаляет запись. Не было записи — восстанавливать нечего, это успех. Повреждённая запись — ошибка, молчаливой догадки нет.
2. **Снимает регистрацию `sora://`** целиком (ключ протокола помечен на удаление при деинсталляции).
3. **Удаляет осиротевший автозапуск**: сканирует `HKCU\…\Run`, удаляет только значения `SoraAutoRun_*`, чья командная строка указывает на исполняемый файл именно этой установки. Значения, указывающие в другой каталог (другая копия Sora), не трогает. Ярлык автозагрузки из папки автозагрузки удаляется как установленный элемент.
4. **Удаляет данные поставляемого клиента в каталоге установки**: `guiNConfig.json`, `statistics.json`, `guiLogs`, `guiTemps`, `guiBackups`, `guiConfigs`. Следствие, о котором честно предупреждаем: **подписки и настройки поставляемого клиента удаление не переживают** — в отличие от обновления поверх. Перед удалением экспортируйте нужные подписки из интерфейса.
5. Не трогает `%APPDATA%\sora-legacy\core` (данные службы ядра и нового клиента) и саму службу `SoraLegacyCore`, если вы регистрировали её вручную: она снимается командой `sora-core --uninstall-service`.

### Ограничение восстановления прокси в новом клиенте

Когда комплект переключится на новый клиент, его собственное восстановление (`--restore-proxy`, нативная реализация без `sysproxy.exe`) будет работать с двумя честными ограничениями, зафиксированными в его коде: восстанавливаются именованные значения HKCU Internet Settings, включая PAC-URL, но **бит AUTO_DETECT не восстанавливается** (он живёт только в бинарном `DefaultConnectionSettings`, который восстановление сознательно не переписывает), а **per-connection записи RAS не переигрываются** (поставляемый путь через `sysproxy.exe` применяет настройки шире). До смены комплекта пользователю работает поставляемый путь из пункта 1 выше.

## Android

Готового публичного релиза для Android нет. То, что существует и проверено в песочнице, — debug-APK, собранный ручным пайплайном (см. [development.md](development.md), раздел «Android»): пакет `one.levvs.sora.legacy`, versionCode 1 / versionName 0.1.0, `minSdk 21` / `targetSdk 34`, размер 279 213 197 байт, SHA-256 `81f55b9fee04d778ff5daa305c19a8fb7f6f42f7b131f6ea430491c474dcaa7c`. Подпись — debug-ключ, сгенерированный пайплайном (алиас `androiddebugkey`): это не релизная идентичность, обновить такой APK поверх будущего релизного нельзя.

Установка в этом виде — только вручную на устройство (sideload): разрешить установку из выбранного источника, открыть APK, при первом подключении подтвердить системный VPN consent-диалог (`VpnService.prepare`). **На устройстве эта сборка не проверялась вообще**: установка, consent-флоу, трафик через туннель, DNS, disconnect/reconnect и always-on — пункты verify-on-device из `android/README.md` (11 пунктов). Не выдавайте debug-APK за проверенный продукт. Удаление — стандартное, средствами Android; данные клиента лежат в app-private `filesDir` (`servers.json` с кредами внутри, `config.json`), `allowBackup=false` — в резервные копии они не попадают и удаляются вместе с приложением.

## macOS

Установщика (pkg/нотаризации) для macOS нет. Установка — скриптами службы из дерева, на Mac, с правами администратора:

1. Соберите демон, хелпер и движки по [development.md](development.md) (раздел «macOS») или возьмите собранные бинари; движки раскладывает `macos/fetch-engines-darwin.sh` и пишет `SHA256SUMS`, без которого ядро движки не запустит (fail-closed).
2. `sudo sh service/darwin/install.sh <каталог с sora-core, sora-ctl и engines/>` — создаёт группу `sora` и добавляет в неё консольного пользователя, ставит бинари в `/usr/local/lib/sora-legacy/`, данные — в `/Library/SoraLegacy/core` (0700, root), plist корневого LaunchDaemon — в `/Library/LaunchDaemons/`, делает bootstrap.
3. Приложение `SoraLegacy.app` собирается Xcode-проектом на Mac (см. development.md); отдельного шага установки у него нет — это обычное AppKit-приложение.

Честные границы: в этой среде ничего из перечисленного на Mac не запускалось (verify-on-mac — 8 пунктов в `macos/README.md`). Пол демона и хелпера — macOS 12.0: на более старой системе клиент запустится и объяснит, но служба работать не будет. На Apple Silicon ниже macOS 26 upstream-бинаря sing-box нет — часть планов там честно не поедет. Kill switch на macOS не форсится (`NoopFirewall`): клиент показывает запрос, а не защиту. Удаление: `service/darwin/uninstall.sh` (bootout и удаление бинарей; данные и логи сохраняет, `--purge` удаляет и их; группу `sora` сознательно не удаляет, каталог сокета `/var/run/sora` тоже остаётся).

## iOS

Публичной установки для iOS нет и в этом виде быть не может: сборка, подписи и распространение — только через Mac с Xcode и Apple Developer аккаунтом по спеке `ios/BUILD-MAC.md`:

1. На Mac собираются оба xcframework (Libbox штатным `build_libbox` пина 1.12.12, Mobileapi официальным gomobile с `-iosversion 13.0`).
2. Проект генерируется XcodeGen из `ios/project.yml` (приложение `one.levvs.sora.legacy` + расширение PacketTunnel), подписывается командой владельца; App Group `group.one.levvs.sora.legacy` и NetworkExtension-capability должны быть зарегистрированы на оба App ID.
3. Установка на устройство — из Xcode или через TestFlight; для TestFlight/App Store отдельно нужен разбор экспортного контроля шифрования (`ITSAppUsesNonExemptEncryption`) — вопрос владельца, в дереве не решён.

Пол — iOS 13.0 (вывод из пина — в `ios/BUILD-MAC.md` §1 и в [platforms.md](../legacy/docs/platforms.md)). В этой среде iOS-сборка не собиралась и на устройстве не проверялась: verify-on-mac — 11 пунктов в `ios/BUILD-MAC.md` §7, включая Keychain round-trip и установку именно на iOS 13. Удаление — стандартное, средствами iOS; креды серверов при этом уходят вместе с Keychain-записями приложения, tunnel exchange в App Group — вместе с контейнером.
